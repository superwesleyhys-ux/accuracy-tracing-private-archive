# 为什么新版大部分任务跑不通

本次复核对象是 pilot 01 的原始响应、冻结执行代码、修复后的当前代码，以及新的离线状态反例。没有进行新的付费模型调用，没有修改旧题、旧答案或旧评分。

结论：**最强的直接解释是分解调用的工作量与单次完成预算不匹配；失败又通过共享首轮传播到后续三个组。另有已经观察到的状态更新约定冲突和新复现的校验缺口。预算、状态与实验测量是不同层的问题，不能用“多循环几次”一并解决。**

1. **先区分 30 个任务失败和独立失败事件。**

40 格结果里，30 格失败：7 个 Accuracy 首轮分解失败，导致 21 个后续分支不执行；p04 独立采样又出现一次分解失败；原版 p05 因两次 API 限流类错误而失败。共 8 次 Accuracy 分解返回失败、2 次没有成功响应的原版请求。21 个派生失败不是另外 21 次模型试验。

首轮没有有效验证结果时，拒绝生成共享检查点是合理的完整性要求。问题在于这一首轮的可用性没有先校准，就直接运行五组矩阵。后续多轮无法修复一个尚不存在的首轮结果。

2. **2,500 限制的是完成总量，不是可见正文的额度。**

官方 Chat Completions 定义表明，`max_completion_tokens` 同时覆盖可见输出和推理 token；官方推理说明也描述了预算耗尽时可能连正文都尚未输出的情况。不能把 Responses 的 `incomplete_details` 字段直接套到本次 Chat Completions 日志上，也不能凭空恢复旧的 `finish_reason`。[参数定义](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create) · [推理预算说明](https://developers.openai.com/api/docs/guides/reasoning)

8 次失败具有同一可见特征：返回实际模型与响应 ID、完成量恰为 2,500、正文为空、包装器记录 `RuntimeError`。各自当时的累计用量和耗时都未触及 36,000/600 秒的整组上限。SDK 身份验证或 JSON schema 请求被服务器拒绝，不能解释这些有响应 ID 和实际生成用量的记录。空正文如果已进入 `json.loads`，会记录另一种异常；这批错误发生在语义解析前。

因此，可以定位到**单次完成返回的验收阶段**。最高优先级假设是完成预算耗尽，旧日志仍不能区分拒绝与非正常结束，也没有推理 token 明细。不能断言 2,500 个 token 全部用在推理上；完成总量还可能包括其他不可见结构 token。[token 计数说明](https://developers.openai.com/api/docs/guides/token-counting)

3. **原版与新版实际上承担了不同的单次工作量。**

下表仅汇总成功调用，输出量为 API 回执的完成 token，不能据此估算失败请求本来需要多少。已排除共享记录复制；原版主流程排除了公共答案提取器。

| 调用组 | 成功调用数 | 完成 token 中位数 | 成功最大值 | 单次上限 |
|---|---:|---:|---:|---:|
| 旧五题实验中的 Accuracy 分解 | 16 | 984 | 1,746 | 2,500 |
| 本轮原版主流程 | 121 | 691 | 1,380 | 2,500 |
| 本轮 Accuracy 分解 | 10 | 2,162.5 | 2,457 | 2,500 |

本轮 Accuracy 还有 8 次失败分解。p04 首轮第一次分解成功使用 2,457，只剩 43 token 的空间。它的单次任务要同时生成片段、关系、缺口、解决记录、来源发现、说明和回访请求，还要满足引用、偏移、编号、层级与时间语义。自动生成的 Analysis schema 有 7 个顶层字段、63 次嵌套属性出现；这不表示每次必须生成 63 个非空字段，但说明接口承担的不仅是一句真假判断。

旧题成功不能外推到这批材料。数据、提示、任务形态和并发配置都变化了，旧/新中位数差不能被解释为单一模型退化。相同上限也是一种有效的运行约束比较，但尚不能识别同等工作负荷下的循环认知收益。

失败分解的输入为 1,668–2,336 token，成功分解覆盖 1,667–4,089。存在更大的输入仍成功，因此没有证据支持简单的“输入太长就失败”解释。限制源于输出预算与任务复杂度的假设更符合现象，仍需控制变量实验。

4. **循环中的状态更新确实有独立缺陷。**

p04 的标签一直为反驳；第二轮却移除了 m07 的来源发现和缺口解决记录，m08 甚至输出了空分析。返回说明仍称先前片段和解释有依据。旧提示鼓励省略已有发现，引擎却以完整替换的方式重建图，因而把省略当作撤回。

这解释了为什么溯源状态从 `original_material_located` 变为 `partial`，以及为什么固定分解组没有同样变化。第三轮恢复部分解决记录、仍没有来源发现。不能由此断定原来那条来源发现一定正确，p04 的来源维度没有外部评分资格；但“仍有依据”与“从现行图删除”之间的约定张力有日志证据。

当前提示已经明确完整替换，并允许有依据的撤回。它仍依赖模型遵守提示；加长输出上限可能提高返回率，却不会自动修好状态语义。

5. **新的离线反例显示程序校验仍不够。**

可复现脚本：[diagnose_state_contract.py](../experiments/diagnose_state_contract.py)。独立复跑结果：[DIAGNOSIS_STATE_PROBES.json](DIAGNOSIS_STATE_PROBES.json)。这些是人工构造的离线反例，不是新增新闻模型测试。

- 两篇内容相反的材料各自返回忠实引用，但片段使用相同编号。引擎不报冲突，只保留后写的片段；重复观察未改变的第一篇材料后，现行片段改变，而两份分析内容都没变。这证明当前图投影会受更新顺序影响。
- 分解器和验证器都能提交一个从未注册过的缺口解决记录，引擎接受且 `assessment_valid=True`。这个标志表示通过当前程序检查，不等于语义正确。
- 跨材料引用本身合理，不能全面禁止。但发现由哪篇材料或哪个操作拥有、谁能改写谁，需要明确规定；目前部分规则只存在于提示里。

这些缺口不能解释首轮 7 次传输失败，因为那些任务尚未进入相关后续阶段。它们说明即使先把返回率修好，系统仍可能在不报错的情况下丢失或污染溯源结构。**新复现的引擎校验问题尚未修复。**

6. **单元测试通过不是线上可用性证据。**

154 项离线测试覆盖了许多程序规则，其中模型适配器集成使用的是预先构造的理想响应。它们没有测出真实模型在当前 schema、提示和上限下的返回分布，也没有阻止上述重复编号和未知缺口反例。程序符合已编写的断言，不能推出断言已经覆盖真实模型所有行为。

本轮强制三轮仍然只重读固定材料。这是隔离重复推理的实验对照，不是开放网络溯源演示。每次重读应说明检查了什么、发现是否变化、变化依据在哪里；单纯再生成一份全图会同时增加成本和状态漂移机会。

7. **接下来应该按因果关系修复，而不是直接加轮数。**

先做小规模开发实验，固定模型、可支持且明确记录的推理档位、材料与调用上下文。将单次预算与结构化任务规模作为两个因素：

| 组 | 分解接口 | 单次预算 | 检验的问题 |
|---|---|---|---|
| A | 现有完整接口 | 2,500 | 复现原故障 |
| B | 与 A 相同 | 预先固定的更高值 | 预算是否限制完成 |
| C | 拆小任务、程序生成可确定字段 | 2,500 | 单次任务负担是否是因素 |
| D | 与 C 相同 | 与 B 相同 | 两项变化是否存在交互 |

具体更高值、案例、重复次数与总预算须在运行前固定；本次只完成诊断，未执行此付费实验。记录结束原因、可见/推理用量、结构校验、引用校验、延迟和全部失败。若 B 好转而 A 稳定失败，增强预算解释；若只有 C/D 好转，说明拆分接口更关键；若均无改善，依据新日志转查其他原因，不能无限扩容。

状态层应采用显式、可校验的更新协议：稳定且分域的编号；新增、保留、修订、撤回各有明确含义；解决记录必须对应已登记或历史上已解决的缺口，并检查作用范围；先验证整次更新再提交。完整替换和增量操作都可以，但不能混用。合法撤回必须允许，不采用永久保留旧结论来制造分数单调上升。

每次材料返回仍进入 ψ 分解。可以让 ψ 输出明确的变化操作并由程序验证，不必在每轮重新生成全部编号和重复引用。若某次更新失败，可保留上次有效状态用于审计，但必须标明本轮未完成，不能宣称通过本轮复核。

最后，先让整个流程具备可测的完成率和状态一致性，再用新事件、人工盲审参考答案比较来源正确率、引用关系、修正/改错次数与成本。本次 8 题已经成为开发材料，不应继续当成隐藏评测。

复查数据：[DIAGNOSIS_TRANSPORT_DATA.json](DIAGNOSIS_TRANSPORT_DATA.json)。诊断依据为冻结提交 `8dbca73` 的线上运行，以及修复后提交 `ddb27e5` 的状态引擎。现有输出预算与未明确设置的推理档位尚未改变；本次诊断没有提高调用额度或重跑模型。
